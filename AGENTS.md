## Project

REST API (FastAPI + PostgreSQL) to manage customers, their connected devices and the measurements those devices send.
Technical challenge for Kamleon: correctness, data integrity and clear trade-offs matter more than feature count.

Design decisions, with rejected alternatives and reasons, are in `docs/DECISIONS.md`.
Read the relevant section before changing the data model, constraints, error responses or concurrency behavior. Never contradict it silently: if a task requires changing a decision, stop and ask.

## Commands

- Start the stack (API + Postgres): `docker compose up --build`
- Run tests (needs Postgres running): `uv run pytest`
- Apply migrations: `uv run alembic upgrade head`
- Create a migration: `uv run alembic revision --autogenerate -m "<message>"`, then review the generated file by hand before applying it
- Lint and format: `uv run ruff check --fix` and `uv run ruff format`
- Add a dependency: `uv add <package>` (`uv add --dev <package>` for dev-only)

## Architecture

Request flow: router → service → repository.

- **Routers (`api/`):** HTTP only. Parse and validate input with pydantic schemas, call one service function, map the result or domain errors to HTTP responses (RFC 9457 problem details). No business logic, no database access.
- **Services (`services/`):** use cases and business rules (e.g. reject measurements for inactive devices). Own the transaction boundaries. Raise domain errors, never `HTTPException`.
- **Repositories (`repositories/`):** all database access. Translate integrity errors into domain errors by constraint name.
- **Domain (`domain/`):** enums, domain errors and pure rules. No imports from FastAPI or SQLAlchemy.
- **Schemas vs. models:** pydantic schemas (`schemas/`) define the API contract (e.g. `DeviceCreate` for input, `DeviceRead` for output); SQLAlchemy ORM models (`models/`) define tables. They are never the same class. Routers convert input schemas into plain arguments for services, and convert the ORM objects services return into output schemas (`from_attributes=True`). Services never import from `schemas/`, and routers never return ORM models directly.

## Non-negotiable rules

1. **Data invariants live in the database.** Properties every stored row must always satisfy (uniqueness, references, allowed values) are enforced by constraints. Application validation may add better error messages, but is never the only guarantee of an invariant. Rules about operations that depend on current state (e.g. rejecting measurements for an inactive device) are enforced in services.
2. **No check-then-insert for uniqueness.** Insert and let the unique constraint decide; never look up first and insert if absent. Choose the pattern by what a duplicate means:
   - **Duplicate is an expected, successful outcome** (idempotent retries, batch processing where one conflict must not abort the rest): `INSERT ... ON CONFLICT (<explicit columns>) DO NOTHING RETURNING`. Example: measurement ingestion.
   - **Duplicate is an error for the client:** plain `INSERT`, catch `IntegrityError`, map it by constraint name to a domain error. Example: device and customer registration (`409`).
   If a new case fits neither, ask before implementing.
3. **Every constraint has an explicit name** (`<table>_<columns>_<key|fkey|check>`). Error mapping depends on constraint names.
4. **Timestamps are always timezone-aware:** `timestamptz` in the database, `AwareDatetime` in schemas. Naive datetimes are rejected, never guessed.
5. **Errors and logging.** Errors are RFC 9457 problem details. Repositories translate driver errors into domain errors (`raise DomainError(...) from e`, keeping the cause); services raise domain errors, never `HTTPException`. Each fact is logged once, by the layer that resolves it:
   - **Errors:** log or return, never both. Only the global exception handler logs them, with their full cause chain: `4xx` at `warning` without stack trace, `5xx` at `error` with stack trace.
   - **Outcomes that are not errors** (e.g. duplicate measurement, measurement id conflict inside a batch) do not raise exceptions; the service logs them once, where they are resolved.
   - Never log measurement values or other health data.
6. **Migrations:** every schema change is a new migration. Never edit a migration that has been applied. Review autogenerated migrations by hand.
7. **Tests run against real PostgreSQL, never SQLite.**
   - Every endpoint has a success test and one test per documented error case (see *Error mapping* in `docs/DECISIONS.md`).
   - One test for the global exception handler: an unexpected error returns `500` as problem details without leaking internals (no stack traces, no database messages).
   - Concurrency-sensitive behavior has explicit tests: simultaneous retries of the same measurement, simultaneous registration of the same serial.
8. **No new dependencies without asking.**


## Definition of done

A task is done only when all of these hold:

1. `uv run pytest` passes, including new tests for the change (see rule 7). Never report a task as done without running the tests.
2. `uv run ruff check` and `uv run ruff format --check` pass.
3. If the schema changed: a new migration exists, has been reviewed by hand, and `alembic upgrade head` and `alembic downgrade -1` both run cleanly.
4. Documentation matches the code: new or changed endpoints have a `curl` example in `README.md`; new error cases appear in *Error mapping* in `docs/DECISIONS.md`.
5. No `TODO`, commented-out code or debug prints are left behind.
6. The final message summarizes what changed, how it was verified, and anything left undone or any decision that needed an assumption.
