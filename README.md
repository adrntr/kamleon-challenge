# Kamleon devices API

REST API (FastAPI + PostgreSQL) to manage customers, their connected devices and the measurements those devices send. Design decisions and their trade-offs are in [`docs/DECISIONS.md`](docs/DECISIONS.md).

## Running

```bash
docker compose up --build
```

This starts three services:

- `db`: PostgreSQL 18, published on host port 5432.
- `migrate`: runs `alembic upgrade head` once and exits.
- `api`: starts only after `migrate` succeeds, and listens on http://localhost:8000.

If host port 5432 is already taken, publish Postgres on another port, for example `DB_HOST_PORT=5433 docker compose up --build`, and use that port in the URLs below.

## API documentation

With the stack running, FastAPI serves the generated OpenAPI documentation:

- Swagger UI (interactive, can send requests): http://localhost:8000/docs
- ReDoc: http://localhost:8000/redoc
- OpenAPI schema (JSON): http://localhost:8000/openapi.json

The `curl` examples for every endpoint are in *Endpoints* below; the reasoning behind the contract is in `docs/DECISIONS.md`.

## Demo

With the stack running, `scripts/demo.sh` walks through the main flows one step at a time (press Enter to run each step): register a customer and a device, a duplicate serial (`409`), a batch (`201`), its retry (`duplicate`), a mixed batch (`207`), deactivation and a rejected ingestion (`409 device-inactive`), and the final query.

```bash
scripts/demo.sh                       # BASE_URL defaults to http://localhost:8000
DEMO_NO_PAUSE=1 scripts/demo.sh       # run every step without pausing
```

Each run registers a new customer and device, so it can be repeated on the same database.

## Tests

The tests run against a real PostgreSQL database, the `db` service, from the host. They need [uv](https://docs.astral.sh/uv/).

```bash
cp .env.example .env    # DATABASE_URL and TEST_DATABASE_URL for the host
docker compose up -d db
uv run pytest
```

The tests create the `kamleon_test` database if it is missing and migrate it to head. They refuse to run against a database whose name does not end in `_test`, because they truncate tables.

Lint and format: `uv run ruff check` and `uv run ruff format --check`.

## Migrations

```bash
uv run alembic upgrade head      # apply
uv run alembic downgrade -1      # revert the last one
```

Alembic reads the database URL from `DATABASE_URL`, the same setting the API uses. It only accepts the `postgresql+psycopg://` scheme.

## Endpoints

### Health

Liveness: the process responds. It never touches the database.

```bash
curl -i http://localhost:8000/health/live
# 200 {"status":"ok"}
```

Readiness: the database answers.

```bash
curl -i http://localhost:8000/health/ready
# 200 {"status":"ok"}
# 503 application/problem+json if the database is unreachable
```

### Customers

Register a customer. The email is lowercased before storing.

```bash
curl -i -X POST http://localhost:8000/customers \
  -H 'Content-Type: application/json' \
  -d '{"name": "Ana García", "email": "ana@kamleon.com"}'
# 201 + Location: /customers/{id}
# 409 email-already-registered, 422 validation-error
```

Retrieve a customer.

```bash
curl -i http://localhost:8000/customers/{customer_id}
# 200
# 404 customer-not-found
```

### Devices

Register a device for a customer. It starts as `active`.

```bash
curl -i -X POST http://localhost:8000/customers/{customer_id}/devices \
  -H 'Content-Type: application/json' \
  -d '{"serial_number": "KM123"}'
# 201 + Location: /devices/{id}
# 404 customer-not-found, 409 serial-already-registered, 422 validation-error
```

List the devices of a customer.

```bash
curl -i http://localhost:8000/customers/{customer_id}/devices
# 200 {"items": [...]}
# 404 customer-not-found
```

Retrieve a device by id.

```bash
curl -i http://localhost:8000/devices/{device_id}
# 200
# 404 device-not-found
```

Set the status of a device (`active` or `inactive`). Idempotent: setting the current status returns `200` and leaves `updated_at` unchanged.

```bash
curl -i -X PATCH http://localhost:8000/devices/{device_id} \
  -H 'Content-Type: application/json' \
  -d '{"status": "inactive"}'
# 200 the device
# 404 device-not-found, 422 validation-error
```

Find a device by serial number (the list is empty if none matches).

```bash
curl -i 'http://localhost:8000/devices?serial_number=KM123'
# 200 {"items": [...]}
# 422 validation-error if serial_number is missing or empty
```

### Measurements

Ingest a batch of 1 to 1000 measurements. Each one carries a `device_measurement_id` generated by the device; a retry with the same id and payload is reported as `duplicate`, not stored twice.

```bash
curl -i -X POST http://localhost:8000/devices/{device_id}/measurements \
  -H 'Content-Type: application/json' \
  -d '{"measurements": [{"device_measurement_id": "0192a7c4-0001-7a3e-8b1f-3c2d4e5f6a70", "type": "ph", "unit": "pH", "value": 7.41, "timestamp": "2026-10-06T09:00:00+02:00"}]}'
# 201 {"summary": {...}, "results": [{"device_measurement_id": "...", "status": "created"}]}
# 207 mixed result, 422 batch-rejected (every measurement rejected, with summary and results)
# 404 device-not-found, 409 device-inactive, 422 validation-error
```

Query a device's measurements in the half-open range `[from, to)`, oldest first. Without `from`/`to`, the last 24 hours; `type` and `limit` (default 1000, max 5000) are optional.

```bash
curl -i 'http://localhost:8000/devices/{device_id}/measurements?type=ph&from=2026-10-06T00:00:00Z&to=2026-10-07T00:00:00Z&limit=1000'
# 200 {"items": [{"id": "...", "device_measurement_id": "...", "type": "ph", "value": 7.41, "unit": "pH", "timestamp": "2026-10-06T07:00:00Z"}], "has_more": false}
# 404 device-not-found
# 422 validation-error (from/to without a UTC offset, from not earlier than to, limit out of range)
```

### Errors

Every error response is an RFC 9457 problem details document (`application/problem+json`):

```bash
curl -i http://localhost:8000/does-not-exist
# 404 {"type":"https://api.kamleon.example/problems/not-found","title":"Not Found","status":404,"instance":"/does-not-exist"}
```

The full list of error cases is in *Error mapping* in `docs/DECISIONS.md`.

## Main technical decisions

A summary; each decision, with the rejected alternatives and the reasons, is in [`docs/DECISIONS.md`](docs/DECISIONS.md).

- **Invariants live in the database.** Uniqueness (serial number, email), ownership, references and allowed values (device status, `(type, unit)` pairs, non-blank text, lowercase email) are named constraints, so they hold for every writer, not only the API. The application adds clear `422` messages on top. The one rule that depends on current state (no measurements for inactive devices) is enforced in the service.
- **No check-then-insert.** Registration does a plain `INSERT` and maps the `IntegrityError` to `409` by constraint name, so two simultaneous registrations of the same serial or email cannot both succeed.
- **Idempotent ingestion with a device-generated id.** Each measurement carries its own `device_measurement_id` (UUID), generated by the firmware when the measurement is taken; the database enforces it as unique per device (`UNIQUE (device_id, device_measurement_id)`). Batches are stored with one multi-row `INSERT ... ON CONFLICT (device_id, device_measurement_id) DO NOTHING`: a retry with the same payload is a `duplicate` (success), the same id with a different payload is a `measurement-id-conflict`.
- **Partial batches.** Valid measurements are stored even if others in the batch fail, with a result per measurement: `201` all stored, `207` mixed, `422 batch-rejected` all rejected. One firmware bug in one measurement does not block the rest on every retry.
- **No lock between ingestion and deactivation.** Deactivation applies to every request that arrives after it commits; an ingestion already in flight may complete (a window of milliseconds).
- **Status changes set a target state** (`PATCH` with `{"status": "inactive"}`), never toggle, so retries and concurrent requests are safe.
- **Timezone-aware timestamps everywhere** (`timestamptz`, `AwareDatetime`): naive datetimes are rejected, never guessed.
- **Errors as RFC 9457 problem details**, with a stable `type` per case, so clients branch on the type instead of the message
- **Indexes for the main query:** `(device_id, "timestamp", type)` serves a device's time range, with or without `type`, already ordered by time.
- **UUIDs:** v4 for customers and devices (not guessable, no volume leak), v7 for measurements (insert locality in the largest table), all generated in the application.
- **Deleting a customer cascades** to their devices and measurements (GDPR right to erasure).
- **Stack:** async FastAPI + SQLAlchemy 2 + psycopg 3 + Alembic; tests against real PostgreSQL, including deterministic concurrency tests.

## Assumptions

The requirements leave these open; each one is explained in `docs/DECISIONS.md`.

- **The API is internal** (Kamleon applications and administrators), so there is no authentication and a `409` may reveal that an email is registered.
- **Emails are case-insensitive:** they are stored lowercased, so `Ana@kamleon.com` and `ana@kamleon.com` are the same customer (the second registration returns `409`).
- **`inactive` means retired or consent withdrawn:** nothing more is accepted from the device, including measurements taken before the deactivation but uploaded after it.
- **The firmware generates a UUID per measurement** and reuses it on every retry, including after reboots.
- **Measurement types and units are a closed list** seeded by a migration (units as ASCII codes such as `degC`, `uA`); unregistered pairs are rejected. The list itself is an assumption.
- **A device belongs to exactly one customer for its whole life:** no unassigned devices and no transfers between customers.
- **Devices measure few types, and queries across all types are the most common for data analysis** (sync, export, a device's timeline), so the index `(device_id, "timestamp", type)` favors time order. If the real use case were different (mostly one type at a time, e.g. one chart per metric, on devices with many types), the index order would change to `(device_id, type, "timestamp")`, decided with real query data.

## Known limitations

- **No authentication or authorization** (see *Security proposals*).
- **No pagination on measurement queries:** a response is capped at `limit` (max 5000) with `has_more: true`; the only way to get the rest is narrowing the time range.
- **Measurements uploaded after a deactivation are rejected**, even if they were taken while the device was active.
- **Ingestion vs. deactivation race:** a request already in flight when the deactivation commits may still store its measurements (milliseconds).
- **Measurements with an unregistered `(type, unit)` pair are lost** until the firmware is fixed or the pair is registered by a migration.
- **No endpoints to delete customers or devices, or to register measurement types:** the behavior is defined in the schema, but not exposed.
- **Deleting a customer with millions of measurements is one long transaction.**
- **During a unit transition**, a query filtered only by `type` can return mixed units (each measurement still carries its own `unit`).

## What I would improve with more time

- **Authentication and authorization:** a credential per device (revoked on deactivation) and OAuth 2.0 tokens for people, with end-user routes such as `GET /me/devices` so a user cannot read another customer's data by changing an id (see *Security proposals*).
- **Cursor (keyset) pagination** for measurements, ordered by `("timestamp", id)`, returning a `next_cursor`.
- **`DELETE /customers/{id}`** for GDPR erasure requests, with **asynchronous deletion** in batches for customers with large histories.
- **An admin endpoint to register measurement types** without a migration.
- **Unit conversion on reads** to a unit requested by the client.
- **Device transfers:** store on each measurement the customer that owned the device at measurement time, and filter reads by it.
- **Recommend UUIDv7 in the firmware contract** for better index locality on the idempotency index.

## GDPR

The API stores personal data (customer name and email, device serial numbers) and health data (measurement values). Logs are written so that they do not become a second copy of it:

- **Measurement values are never logged.** Ingestion outcomes that are not errors (duplicates, rejected items) are logged as one aggregated line per outcome, with the device id, count, type and unit only.
- **Client errors (`4xx`)** are logged at `warning` with the method, path, status and problem type only. The problem `detail` is not logged, since it can contain personal data (e.g. the email in `email-already-registered`). The path carries ids (`customer_id`, `device_id`), never emails or names.
- **Server errors (`5xx`)** are logged at `error` with the cause chain and stack trace, which are needed to fix the bug. They are unexpected by definition, so they are rare, but a database error message in the cause can quote the values of the failing row.

## Security proposals

Proposals, not implemented in this challenge (the requirements exclude authentication and production infrastructure). What is already implemented for data protection is described in *GDPR*.

1. **GDPR: pseudonymized analytics.** Measurements already contain no direct identifiers: they reference a device, and the name and email live only in `customers`. Analytics and data exports would only get access to `measurements`, never to `customers`, so health data can be analysed without knowing whose it is. Full anonymization (e.g. aggregated data only) would be required before sharing data outside the company.
2. **Encryption: TLS on every connection.** Devices and applications reach the API only over HTTPS, so measurements (health data) cannot be read or modified in transit. The connection between the API and the database is encrypted too (locally they talk over the Docker network without TLS).
3. **Secrets in a secrets manager.** Database credentials come from a secrets manager instead of an `.env` file.
4. **Authentication for devices and for people.** Each device authenticates with its own credential, so the API knows which device is sending and a device can only send its own measurements; deactivating a device also revokes its credential. People and applications authenticate with tokens (OAuth 2.0), and each user can only access their own customer's data.

## Monitoring and observability (proposal)

**Tools:** any standard metrics, dashboards and alerting stack (e.g. Prometheus + Grafana, or a managed service like Datadog), plus structured logs in a central log store. The tool matters less than what is measured and when the team is alerted.

**What to monitor**
- **API:** requests per second, error rate (`5xx`), and latency (p95) per endpoint.
- **Ingestion:** measurements received per minute, and how many are `created`, `duplicate` or `rejected`, by reason.
- **Database:** slow queries, connection pool usage, disk usage.

**How issues are detected**
- `5xx` rate or latency above a threshold for several minutes.
- A rise in rejected measurements: usually a firmware bug.
- A sudden drop in measurements received: devices cannot reach the API, even if the API looks healthy.

**How the team is alerted**
- **Critical** (API down, ingestion stopped): an urgent notification (call or SMS) to the engineer on duty.
- **Warning** (rejections rising, slow queries): a message in the team's Slack channel.

## AI-assisted development

**Tools**
- **Claude (chat):** design discussion before writing code. I used it to challenge my decisions; the decisions and their reasons are mine and live in `docs/DECISIONS.md`.
- **Claude Code:** coding agent for the implementation, tests and documentation updates.
- **Gemini:** a second opinion on one concurrency question.

**How I worked with the agent**
- **A clean context per task:** every endpoint or block of work started in a new session. `AGENTS.md` and `docs/DECISIONS.md` are loaded fresh each time, so the agent works from the current decisions instead of an outdated conversation, and earlier attempts do not leak into the next task.
- **The right model for each task:** a larger model for the delicate parts (ingestion, idempotency, concurrency) and a smaller, cheaper one for routine endpoints and documentation, to keep cost proportional to the difficulty of the task.
- **Plan before code:** for the scaffolding and the ingestion, the agent first proposed a plan and listed its open questions; I answered them and updated `docs/DECISIONS.md` before any code was written.

**What I used them for**
- Discussing the data model, idempotency, concurrency and error contract before any code existed.
- Generating the scaffolding, endpoints and tests, one endpoint at a time, always against the contract already written in `docs/DECISIONS.md`.
- Reviewing: a fresh agent session reviewed the finished code against `AGENTS.md` and `docs/DECISIONS.md` without changing anything, and I decided what to fix.

**One suggestion I rejected**
To close the race between ingestion and device deactivation, the AI proposed locking the device row with `SELECT ... FOR SHARE` on every ingestion. I rejected it: with a continuous stream of measurements, new share locks can keep arriving while the deactivation waits, so a device could become impossible to deactivate under load (starvation), and every ingestion would pay for a lock to close a window of milliseconds. A second assistant claimed Postgres queues lock requests in order, so this could not happen; I checked Postgres' own documentation and source notes and confirmed it can. I kept ingestion lock-free and documented the exact guarantee instead. More cases are listed in `docs/AI_LOG.md`.

**How I validated the generated code**
- **Tests against real PostgreSQL**, never SQLite, including deterministic concurrency tests: one connection holds an uncommitted insert, and the test checks in `pg_stat_activity` that the API request is really blocked on that lock before committing or rolling back.
- **Checking the database, not only the Python:** I reviewed the migrations in `psql` (constraint names, types, cascades, indexes) and ran `downgrade` and `upgrade` on a clean database.
- **Manual checks against the running stack** with the `curl` examples in this README.
- **Reviewing every change against `docs/DECISIONS.md`**, and recording each correction in `docs/AI_LOG.md`: what the AI proposed, what I changed, and how I verified it.

**AGENTS.md and skills (mine; no public ones)**
- **`AGENTS.md`:** loaded by the agent in every session. It points to `docs/DECISIONS.md` and sets the commands, the layered architecture and the non-negotiable rules: data invariants enforced by named database constraints, no check-then-insert, how errors and logs are handled, no new dependencies without asking, and tests for every documented error case and for concurrency. It also defines when a task is done.
- **`add-endpoint` skill:** a step-by-step procedure for adding or changing an endpoint: check the contract first (and never change an existing one without approval), then schemas, domain, repository, service, router, tests (including forcing concurrent interleavings deterministically), documentation and a final verification.
